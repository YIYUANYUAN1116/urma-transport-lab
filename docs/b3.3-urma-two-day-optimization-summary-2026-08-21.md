# URMA Transport Lab 两日性能优化总结（2026-08-20～2026-08-21）

## 1. 结论

本轮优化已经把性能问题从“transport 架构受限”推进到“应用数据处理受限”。

同节点真实 UB provider 实验表明：

- fixed-TX 8 GiB 最佳达到 `406.27 Gbit/s`，与约 `398.95 Gbit/s` 的
  `urma_perftest send_bw` 参考值处于同一档位；
- fixed-TX 64 GiB 长测约 `389 Gbit/s`，说明 queue、completion moderation、WR
  retirement 和 provider 热路径已经不再是主要瓶颈；
- dynamic memory 8 GiB 达到 `59.57 Gbit/s`，当前受 Parent 单核
  memory-to-registered-memory copy 限制；
- mmap file + Child CRC32/pwrite 达到 `44.16 Gbit/s`，相对批量 `pread` 路径提升约
  `2.24x`；
- buffered 真实文件系统复测稳定在 `43.57 Gbit/s` 左右，当前瓶颈是 Parent copy 和
  Child 文件处理反压的组合，而不是 URMA provider 带宽。

因此 demo 已经完成 URMA transport foundation 和单流文件数据路径的性能可行性验证。
后续不应继续把 Dragonfly 的多 Piece、Scheduler、Storage 和生产资源管理复制进 demo；
应冻结 demo 功能，解决跨节点环境后进入真正的 Dragonfly URMA adapter。

## 2. 证据口径

本文按以下口径区分结论：

- **同节点实验验证**：在真实 `udmac0d1e2` provider 上获得，但不等价于跨节点网络结果；
- **源码确认**：由当前 lab、UMDK 或 Dragonfly2 候选分支源码确认；
- **架构推断**：由计数器、CPU 时间和数据路径推导；
- **待环境验证**：跨节点 provider、路由及设备配置尚未通过；
- **待 Dragonfly 集成验证**：尚未在真实 Piece/Storage/Downloader 链路中运行。

Dragonfly RDMA 参考来自当前本地 Dragonfly2 候选分支，不代表上游 main 已发布实现。

## 3. 优化前的主要问题

早期实现存在以下结构性限制：

1. SEND completion 与每个发送强绑定，CQE 数量和发送数近似相同；
2. TX slot 回收缺少有效的 completion frontier，难以安全扩大 outstanding WR；
3. RX credit、物理 RX slot 和应用消费生命周期没有清晰分层；
4. SEND/RECV 热路径执行大量空轮询，曾出现数亿次 poll call；
5. RX CQE 后复制到普通 heap buffer，产生额外 bounce copy；
6. CRC32 和文件写入串行阻塞 receive/repost；
7. 文件 Parent 每个 64 KiB SEND 前执行一次 `pread`；
8. dynamic/file payload 每次发送前都需要填充 registered TX，无法区分 provider 上限与
   payload producer 上限；
9. 大 `bytes` fixed-TX case 曾执行 O(transfer bytes) 初始化，导致 JettyCreated 前等待时间
   随测试规模增长。

## 4. SEND completion 与 TX reclaim

SEND 路径改为 moderated completion：普通 WR 可以不产生 CQE，定期 signaled WR 建立
retirement frontier。一个 signaled completion 可以安全覆盖并回收其之前已按序完成的
SEND WR。

当前 TX 生命周期为：

```text
Free
-> Allocated / Prepared（CPU 可写，provider 尚无引用）
-> SendPosted（CPU 不可写）
-> signaled completion frontier
-> SendCompleted / Free
```

安全约束：

- posted WR 完成前绝不复用 slot；
- prepared batch 必须 post 或显式 discard；
- fill 失败释放整批未提交 slots；
- partial post 失败只释放尚未提交的尾部；
- 已提交 WR 由 completion 或 shutdown drain 回收；
- 每个批次最后一个 WR 强制 signaled，避免 moderation 与 batch 长度不整除时缺少 frontier。

## 5. RX credit 与 registered window lease

RX 路径将协议 credit、物理 slot 和应用 ownership 分离：

```text
预投 RECV
-> RX CQE
-> registered RX window lease
-> CRC32 / pwrite读取同一注册内存
-> lease完成
-> slot回收并repost
-> 返回remote credit
```

credit 只在物理 slot 重新 post 成功后返回，避免远端把“应用已收到”误当成“buffer 已可
复用”。RX lease 存活期间 slot 不能 repost，Segment 也不能被安全注销。

这一改动消除了 RX bounce copy，并把早期数亿级空 poll 降到可控范围。显式 credit
落地后的 2 GiB memory 测试从约 `167 MiB/s` 提升到 `2246.84 MiB/s`。

## 6. 并行 CRC32 与有序 combine

Child 将多个 completed registered windows 分派给多个 worker：

- 每个 window 独立计算 CRC32；
- file scenario 同时从相同只读 lease 执行 positional write；
- worker 可以乱序完成；
- CRC32 使用 `combine` 按 wire order 合并；
- lease retirement 同样按 wire order 进行；
- slot repost 成功后才返回 credit。

配合更深 RX backing，normal memory 2 GiB 达到 `6938.63 MiB/s / 58.21 Gbit/s`；
后续 8 GiB dynamic memory 达到 `7101.76 MiB/s / 59.57 Gbit/s`。

## 7. fixed-TX provider 基线

fixed-TX profile 复用一个不可变 registered payload，排除每个 SEND 前的 payload
构造和 memcpy。expected CRC 通过二进制 CRC combine 计算，初始化复杂度从
O(transfer bytes) 降为 O(chunk size + log chunk count)。

同节点实验结果：

| Case | Size | Window | 吞吐 |
|---|---:|---:|---:|
| fixed-TX + CRC32 workers | 8 GiB | 64 | `48431.63 MiB/s / 406.27 Gbit/s` |
| fixed-TX 长测 | 64 GiB | 64 | 约 `46399 MiB/s / 389.23 Gbit/s` |
| `urma_perftest send_bw` 参考 | - | - | `47558.59 MiB/s / 398.95 Gbit/s` |

这证明同节点 provider 热路径已经接近 perftest；它不代表真实文件传输也应达到 400
Gbit/s，也不代表跨节点链路已经验证。

## 8. 文件 Parent 路径演进

文件发送依次经历：

```text
64 KiB pread -> SEND
-> 4 MiB批量pread -> 64个64 KiB SEND
-> finished-file只读mmap
-> 4 MiB registered TX window
-> A/B双TX ring重叠copy和SEND
```

### 8.1 直接填充 registered TX

首先移除普通 heap chunk 到 TX slot 的第二次 memcpy，让 positional read 直接写入
registered memory。8 GiB file 约为 `2233 MiB/s`。

### 8.2 4 MiB 批量 pread

window=64、chunk=64 KiB 时，一次填充连续 4 MiB registered range，再提交 64 个合法
SEND WR。`pread` syscall 数降低约 64 倍，但吞吐仍约 `2344 MiB/s`，证明瓶颈已经不是
syscall 次数，而是串行 page-cache-to-registered-memory copy。

### 8.3 mmap + 双 registered TX ring

参考 Dragonfly2 候选 RDMA finished-piece 路径，Parent 在 START 前建立
`MAP_PRIVATE` 只读映射，使用 `MADV_SEQUENTIAL` 和 `MADV_WILLNEED` best-effort hint。
mmap 失败时自动回退到批量 `pread`。

128 个 TX slots、window=64 时形成两个 4 MiB ring：

```text
copy mmap -> ring A
-> post A的64个SEND
-> A outstanding期间copy mmap -> ring B
-> wait A batch-tail completion
-> post B并重新填充A
```

8 GiB 实验确认：

```text
file_mmap_tx=1
file_pread_calls=0
file_tx_batch_count=2048
file_tx_batch_max_bytes=4194304
tx_ring_windows=2
tx_fill_overlap_batches=2047
```

吞吐达到 `5263.84 MiB/s / 44.16 Gbit/s`，相对批量 `pread` 路径提升约 `2.24x`。

## 9. 当前性能矩阵

| 路径 | 实验结果 | 结论 |
|---|---:|---|
| fixed-TX 8 GiB | `406.27 Gbit/s` | 同节点 provider/queue 基线 |
| fixed-TX 64 GiB | 约 `389 Gbit/s` | 长时间基线稳定 |
| dynamic memory 8 GiB | `59.57 Gbit/s` | Parent 单核 TX fill 限制 |
| mmap file + CRC/pwrite 8 GiB | `44.16 Gbit/s` | 单流真实应用路径 |
| buffered真实文件系统复测 | `43.57 Gbit/s` | 结果可复现 |
| tmpfs output，32 workers | `18.09 Gbit/s` | 高并发 shmem page/lock 争用 |
| tmpfs output，16 workers | `19.25 Gbit/s` | 争用下降但仍受存储侧限制 |
| 真实文件系统，16 workers | `28.85 Gbit/s` | worker不足导致Child尾部积压 |
| TCP userspace file | `16.08 Gbit/s` | 普通blocking read/write参考 |
| TCP userspace file，4 MiB chunk | `14.28 Gbit/s` | syscall减少但单次实验吞吐下降 |
| TCP sendfile | `13.41 Gbit/s` | Parent CPU低，但单次结果受Child/缓存状态影响 |

所有列出的 URMA 正常结果均通过 length 和 CRC32 校验，且最终 outstanding SEND/RECV
归零、`cqe_error=0`。

## 10. 当前瓶颈定位

### 10.1 Dynamic memory

8 GiB dynamic double-ring 数据：

```text
elapsed                 1.1535 s
tx_fill_ns              1.0984 s（约95.2%）
Parent CPU              1.1465 s（约单核99.6%）
remote_credit_wait_ns   2.62 ms（约0.23%）
```

架构推断：瓶颈是单核 memory-to-registered-TX `copy_from_slice`，不是 credit、CQ 或 provider。

### 10.2 Buffered真实文件系统

32 workers 的 8 GiB file 数据：

```text
elapsed                 约1.58 s
tx_fill_ns              约1.24 s
remote_credit_wait_ns   约0.28 s
throughput              43.57 Gbit/s
```

架构推断：Parent mmap copy 与 Child CRC/pwrite 产生的 RX lease/credit 反压共同决定吞吐。

### 10.3 tmpfs

tmpfs 并不自动更快。32 workers 时 Child system CPU 约 `57.8 CPU-seconds`，remote credit
等待约 `2.50 s`；降到16 workers 后 system CPU 降至约 `30.0 CPU-seconds`，吞吐仅小幅升至
`19.25 Gbit/s`。这表明高并发 pwrite 在 tmpfs 上产生页分配或锁争用。

### 10.4 8 GiB transport-only profile

该 profile 为完整 payload 分配约 8 GiB registered RX backing，同时 provider credit 仍为
512。实验中 remote credit wait 达到约 `3.18 s`，吞吐只有 `15.39 Gbit/s`。因此当前大
payload transport-only profile 本身会引入巨型 MR/RX bookkeeping 和 credit 限制，不可
作为硬件上限；fixed-TX/perftest 才是当前 provider 基线。

## 11. TCP 与 URMA 结果边界

当前 TCP 和 URMA 不只是“传输协议不同”，应用数据路径也有多处没有对齐：

| 维度 | TCP userspace | TCP sendfile | URMA |
|---|---|---|---|
| Parent 读文件 | 64 KiB `read`（补充实验为4 MiB） | 内核 `sendfile` | mmap后按4 MiB copy到registered TX |
| Parent并发 | 顺序blocking write | blocking sendfile | 64个outstanding WR |
| Child接收 | heap buffer | heap buffer | NIC直接写registered RX |
| Child写入 | 单线程512 KiB `BufWriter` | 同左 | 4 MiB window、最多32 workers并行pwrite |
| CRC与写入 | 顺序执行 | 顺序执行 | CRC与pwrite并行 |
| RX buffer回收 | 普通heap buffer | 普通heap buffer | lease完成后repost并返回credit |
| 流控 | TCP内核窗口 | TCP内核窗口 | 显式RX credit |
| CPU配额 | 实验中Child绑定1核 | 实验中Child绑定1核 | 实验中Child使用poll core加最多32个worker |
| completion语义 | `write`把数据交给socket buffer；Child最终flush | `sendfile`把数据交给socket；Child最终flush | SEND CQE retirement；Child lease处理后repost |
| `window`参数 | JSON中保留但数据路径不使用 | JSON中保留但数据路径不使用 | 真正限制outstanding WR |

当前已经对齐的口径只有：

- 相同输入长度与expected CRC32；
- 使用同一输出文件系统时采用相同的buffered completion定义；
- steady-state均不包含连接和transport资源初始化；
- Child结束前完成文件flush、长度与CRC32检查；
- 均为单连接、单个逻辑传输。

最大的不公平点位于Child应用处理：

```text
TCP：单核、顺序 recv -> buffered write -> CRC
URMA：多核、registered RX -> 多路 CRC + pwrite
```

其次是Parent source producer不同：

```text
TCP userspace：每个应用chunk执行read + write
TCP sendfile：文件内容不经过用户态payload buffer
URMA：每4 MiB执行mmap copy，并提交64个64 KiB SEND WR
```

因此当前 URMA 相对 TCP 的倍数同时包含 transport、no-bounce、应用并行和文件策略差异，
不能表述为纯协议加速比。TCP 仅作为工程参考；本轮不继续扩建 Dragonfly-like TCP，以免
demo 演变为另一个生产实现。

补充的 8 GiB TCP userspace、4 MiB chunk 单次实验结果为：

```text
throughput                 1702.87 MiB/s / 14.28 Gbit/s
parent read/write calls    2048 / 2048
child read calls           4462
Parent CPU                 4.52 s
Child CPU                  2.97 s
```

相对 64 KiB chunk 的 `16.08 Gbit/s`，4 MiB chunk 将 Parent read/write 调用从各131072次
降到各2048次，Child read调用从131072次降到4462次，但吞吐反而下降约11.2%，Parent和
Child CPU时间也没有下降。该单次实验说明当前TCP userspace瓶颈不是64 KiB syscall数量；
增大应用buffer不能自动提高blocking socket和文件sink的端到端吞吐。缓存、dirty-page
状态和运行顺序仍可能影响单次结果，正式结论需要交错顺序重复测试。

## 12. 与 Dragonfly 候选 RDMA 的对齐程度

已经借鉴并实现：

- finished piece 只读 mmap；
- mmap/page cache copy 到 registered send ring；
- 双 registered TX ring；
- registered RX window lease；
- CRC32 与 pwrite 读取同一 RX window；
- completion 前绝不复用；
- bounded outstanding WR 和显式接收流控。

尚未实现：

- Dragonfly Piece、Downloader、Storage 接口；
- 多 Piece 并发和 Scheduler；
- 共享 endpoint/CQ/progress worker；
- 全局 registered-memory budget 和 best-fit pool；
- peer discovery、fallback、认证、限流和生产 shutdown/error policy。

这些能力应在真正的 Dragonfly adapter 中实现，而不是继续复制到 standalone lab。

## 13. 待解决问题

1. **跨节点环境**：demo 与官方 `urma_perftest` 跨节点均出现 `CR status 2`。由于官方工具
   同样失败，当前证据更指向 UB 网络、EID、路由或 provider 环境，而不是 demo WR 逻辑。
2. **真实网络性能**：所有高性能数字均为同节点实验，不能替代跨节点400G链路验证。
3. **真实持久化**：`buffered` completion 主要反映 page cache 接收能力；不等同于
   `fdatasync` 后的物理盘吞吐。
4. **生产并发**：单个8 GiB逻辑传输与Dragonfly典型64 MiB Piece、多Piece并发不同。
5. **worker模型**：当前 file worker 内部仍为每个window临时创建写线程；可以在真正
   Dragonfly集成时复用其Tokio blocking pool和Storage实现，无需在demo重复建设。
