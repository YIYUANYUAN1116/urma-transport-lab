# B3.1 Build Status: URMA CQ polling optimization

> 更新日期：2026-08-18  
> 阶段：B3.1 JFCE hybrid implementation；真实双节点性能回归待执行

## 基线与问题

真实 UB/UDMA 环境已经验证 bounded SEND pipeline 正常达到配置窗口：W=4 时 `max_outstanding_send=4`，W=8 时为 8；send/recv post 与 CQE 闭合且 integrity 通过。因此本轮不修改协议、codec、window、BufferPool、slot 生命周期或 completion accounting。

256 MiB、payload 32768 bytes 的基线显示：

```text
W=4: 1.482948 MiB/s, 172.6s, poll_calls=690054880
W=8: 1.673647 MiB/s, 152.9s, poll_calls=605618568
empty ratio ≈ 99.999%, Parent/Child process CPU ≈ 100%
```

当前 UMDK 源码确认 `urma_poll_jfc()`/UDMA `udma_u_poll_jfc()` 是非阻塞 CQ owner-bit 检查；CQ 为空时立即返回。原实现每次高层 poll 都无条件检查 send 和 recv 两个 JFC，随后调用 `yield_now()`；在没有其他 runnable task 时 yield 可以立即返回，因此形成高频空轮询。

## 第一版 sleep backoff 实验

第一版使用 64 次 hot poll、64 次 yield、之后每次请求 10 us sleep。真实
W=8、256 MiB 回归保持了所有 correctness/accounting 条件，但结果为：

```text
throughput:                  1.119487 MiB/s
Parent CPU:                  2.553384 s / 228.7 s
Child CPU:                   3.496957 s / 228.7 s
poll_calls:                  7,622,365
sleep_count:                 7,395,779
max_completion_poll_gap_ns:  83,838,020
```

相对 1.673647 MiB/s 基线，吞吐下降约 33%。这证明 timer sleep 虽然显著降低
CPU 和 poll 次数，但会引入不可接受的调度长尾，不能作为 B3.1 最终策略。

## JFCE hybrid 优化

`CompletionPoller` 现在只 poll 存在对应 outstanding WR 的 JFC。例如 Parent payload 阶段不再检查没有 outstanding RECV 的 recv JFC，Child payload 阶段不再检查没有 outstanding SEND 的 send JFC。

Runtime 创建一个由 send/recv JFC 共享的 JFCE。空 poll 使用：

```text
empty streak 1..=64: hot poll + CPU spin hint
after hot phase:      rearm active JFC -> repoll -> wait JFCE
event wakeup:         poll CQ -> ack event -> rearm -> repoll
wait safety timeout:  10 ms
non-empty poll:       streak immediately reset to zero
```

两次 repoll 分别关闭首次 rearm 以及 event ack/rearm 边界的 CQE 竞态。正常 CQE
通过 provider event 提前唤醒，10 ms 只用于丢失/延迟通知时的安全恢复，不是固定
poll interval。UMDK 示例和 UDMA provider 源码已确认 `create_jfce`、`rearm_jfc`、
`wait_jfc`、`ack_jfc` 路径存在；真实设备行为仍需本轮回归验证。

资源顺序为 JFCE -> send/recv JFC，销毁顺序反向执行。原调用点中 poll 后的额外
无条件 `yield_now()` 已删除。错误 CQE、batch routing、`user_ctx`、slot release、
receive credit 和 shutdown drain 仍走原路径。

因 shim native surface 新增 JFCE create/delete/wait/ack/rearm，
`URMA_LAB_SHIM_ABI_VERSION` 从 4 更新为 5。

## 新增指标

保留：

```text
poll_calls
empty_polls
max_outstanding_send
```

新增：

```text
send_jfc_poll_calls
recv_jfc_poll_calls
yield_count
sleep_count
backoff_sleep_ns
jfc_rearm_count
event_wait_count
event_wakeup_count
event_timeout_count
spurious_wakeup_count
event_wait_ns
max_event_wait_ns
max_empty_streak
nonempty_polls
completion_batch_total
avg_poll_batch_milli
empty_poll_ratio_ppm
max_completion_poll_gap_ns
```

`avg_poll_batch_milli / 1000` 是每次 non-empty 高层 poll 返回的平均 CQE 数。`empty_poll_ratio_ppm / 10000` 是百分比。

`yield_count`、`sleep_count`、`backoff_sleep_ns` 为兼容第一版结果而保留，JFCE
hybrid 路径应为零。`event_wait_ns` 是 Parent/Child 在 JFCE wait 中的累计 wall
time，`max_event_wait_ns` 是单次等待最大值。`max_completion_poll_gap_ns` 是返回
CQE 的当前高层 poll 与上一次高层 poll 开始时间的最大间隔，包含 event wait、
调度和调用方工作；它是检测间隔的保守上界，不是硬件 CQE 自身 latency。

Parent/Child 的 counter 通过既有 Done 控制消息汇总；Done 不承载数据面 payload。成功结果仍必须满足：

```text
send_post == send_cqe
recv_post == recv_cqe
current_outstanding_send == 0
current_outstanding_recv == 0
cqe_error == 0
integrity.ok == true
max_outstanding_send == configured_window
```

真实 provider 回归必须在相同 256 MiB、32768-byte payload 上分别跑 W=4/W=8，并与上述基线比较：

- throughput 不低于对应基线；
- Parent/Child CPU time 和每秒 `poll_calls` 明显下降；
- `event_wakeup_count > 0`，且 `event_timeout_count`/`spurious_wakeup_count` 无异常增长；
- 检查 `max_completion_poll_gap_ns`，确认 completion 检测间隔没有出现不可接受的长尾；
- 所有 correctness/accounting 条件继续成立。

当前工作区没有 `/sys/class/ubcore` 或 `/dev/uburma`，因此本地编译/单元测试不能替代 node3/node4 的真实 UB/UDMA 结果。性能目标在真实回归完成前标记为 `awaiting environment validation`。
