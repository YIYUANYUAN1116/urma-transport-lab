## 3. Protocol v3

### 3.1 Frame header

每次 encode 仍生成一条完整 frame。所有多字节整数均为 big-endian。

| Byte | 字段 | 类型 | v3 值/约束 |
|---:|---|---:|---|
| 0..4 | magic | u32 | `0x55524d44` |
| 4..6 | version | u16 | `3` |
| 6..8 | message_type | u16 | Request=3、Metadata=4、Data=5、End=6、Error=7 |
| 8..16 | request_id | u64 | 必须非零 |
| 16..20 | sequence | u32 | Request/Metadata/Error 为 0；End 等于 Data count |
| 20..24 | payload_len | u32 | 必须与 frame 剩余字节完全一致 |

`[设计选择]` v3 沿用已知 message type 数字，但通过显式 `match` 在 wire 数值和 Rust enum 之间转换；不序列化 Rust enum discriminant。v3 不定义 Ping/Pong，M3 Ping/Pong 继续走 v2。

`[已从当前 lab 源码确认]` 当前 slot 上限仍为 64 KiB，因此任意 v3 payload 最大为 `65536 - 24 = 65512` 字节。decoder 同时检查 header 声明长度、实际 frame 长度和该上限。

### 3.2 Metadata v3 payload

| Payload byte | 字段 | 类型 | 说明 |
|---:|---|---:|---|
| 0..8 | offset | u64 | Piece 在 task file 中的起始 offset |
| 8..16 | total_length | u64 | Piece 内容长度；允许 0 |
| 16..18 | digest_algorithm | u16 | 稳定编号，见下节 |
| 18..20 | digest_len | u16 | digest value 的 UTF-8 byte 长度，范围 1..=64 |
| 20..(20+N) | digest_value | N bytes | 不含 algorithm prefix 的 canonical value |

例如 CRC32 数值 `1475635037` 在 Metadata 中编码为 algorithm `1`、length `10`、ASCII bytes `1475635037`；对 Dragonfly 上层输出时转换为 `crc32:1475635037`。

decoder 会拒绝：错误 version、未知 algorithm、少于 20 字节的 Metadata、空或超过 64 字节的 digest、内部 length 与 payload 不一致、非 UTF-8/非法 algorithm value，以及任何 trailing byte。encoder 和 decoder 都受现有 slot payload 上限保护。

### 3.3 Digest algorithm 稳定编号

| Wire number | Algorithm | Canonical value |
|---:|---|---|
| 1 | CRC32 | `u32` 的无前导零十进制字符串；范围 `0..=4294967295` |
| 2 | SHA-256 | 64 个小写十六进制 ASCII 字符 |

`[设计选择]` v3 明确携带 algorithm，CRC32 是 integration Piece 语义；SHA-256 只作为显式兼容能力保留，不是 integration demo 的默认算法。最大 digest value 长度选择 64，恰好容纳 SHA-256 hex，且显著小于 slot 上限。

## 4. Dragonfly CRC32 源码依据

以下结论均为 `[已从 Dragonfly 源码确认]`：

1. `client/dragonfly-client-util/src/digest/mod.rs`：`Algorithm::Crc32` 显示为 `crc32`，分隔符为 `:`，`Digest` 的 `Display` 输出 `algorithm + ":" + encoded`。
2. 同文件的 `calculate_file_digest()`：CRC32 使用 `crc32fast::Hasher`，encoded value 是 `hasher.finalize().to_string()`；测试样例为 value `1475635037`。
3. `client/dragonfly-client-storage/src/io.rs`：`write_range_from_stream()` 对 stream 增量计算 CRC32，并把 `finalize().to_string()` 放入 write response；空 Piece 也按相同规则计算。
4. `client/dragonfly-client-storage/src/lib.rs`：standard Piece 完成路径以 `Digest::new(Algorithm::Crc32, response.hash)` 形成实际 digest，并把其字符串与 downloader 提供的 `expected_digest` 比较。因此该接口实际期望完整字符串 `crc32:<decimal-u32>`。

`[设计选择]` wire 内不重复存储 `crc32:`；`DigestDescriptor { algorithm, value }` 保持结构化信息，`external_string()` 在适配 Dragonfly Downloader tuple 时生成完整字符串。CRC32 parser/descriptor 还拒绝符号、非数字、越界和前导零，避免同一数值存在多个 wire 表示。

`[已从 Dragonfly 源码确认]` util 中通用的 `Digest::from_str()` 另有“CRC32 encoded 长度必须为 10”的限制，但 standard Piece Storage 路径不调用该 parser，而是从 `finalize().to_string()` 直接构造并比较 `Digest`；空 Piece 的现有测试也明确得到 `"0"`。因此本阶段按实际 standard Piece 生成/比较语义接受 `crc32:0`，不做十位补零。`[尚待验证]` 如果未来 Dragonfly adapter 的其他路径改为调用通用 `FromStr`，需单独评估这个上游内部不一致，不能在 wire codec 中静默补零。

## 5. v2/v3 compatibility

`[已从当前 lab 源码确认]`：

- 既有 `Message`、`MessageBody`、`DATA_VERSION = 2` 和 v2 Metadata 48-byte payload 未改变。
- M3 Ping/Pong 继续由 v2 `Message` encode/decode。
- M4 Request/Data/End/Error 和固定 SHA-256 Metadata 的既有测试继续通过。
- v3 使用独立 `IntegrationMessageV3`/`IntegrationMessageBodyV3`；v2 decoder 拒绝 v3，v3 decoder 也拒绝 v2。

`[设计选择]` 这种隔离避免为了 M5.1 重构 transport foundation，也防止同一个 `Message::Metadata` 在相同 version 下产生两种含义。M5.2 必须显式选择 v3 API，不能依赖自动猜测 payload。

## 6. CRC32 helper

- `Crc32Hasher::update/finalize`：供后续 streaming Piece source/sink 增量计算。
- `crc32_bytes`：纯内存 one-shot 计算。
- `crc32_reader`：流式读取并返回 `(crc32, length)`，处理 interrupted read 和长度溢出。
- `format_crc32_digest`：输出 `crc32:<decimal-u32>`。
- `parse_crc32_digest`：只接受 canonical Dragonfly-compatible 格式。

`[已从当前 lab 源码确认]` 这些 helper 当前没有接入 M4 文件传输流程；M4 仍使用 SHA-256，不存在静默行为变化。

## 9. M5.2 接口前置条件

以下是 `[设计选择]`，仅记录后续接入边界，不在 M5.1 实现：

1. transport 需要一个显式 v3 frame send/receive 边界，调用 `IntegrationMessageV3` codec；不得把当前只接受 v2 `Message` 的 API 隐式改义。
2. Parent Piece source 需要产出 `offset`、`total_length`、CRC32 descriptor 和 reader；CRC32 应通过本阶段 helper 流式生成。
3. Child 在 Metadata 校验后需要把 `DigestDescriptor::external_string()` 作为 Downloader tuple 的 digest，并把后续 Data 映射到有界 stream；不能等待完整 Piece。
4. Request 状态机仍需定义 Metadata/Data/End/Error 的时序、sequence/length 校验、背压和 shutdown error 传播。
5. `[尚待验证]` v3 接入现有单-owner synchronous Connection 的最小 API 形态，以及真实 provider 下 v3 Metadata/Data/End 的完整传输，留给 M5.2。
