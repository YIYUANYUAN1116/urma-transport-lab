# B3.2 URMA transport 性能优化复盘（2026-08-19）

## 1. 结论

今天以 `urma_perftest send_bw` 的源码和真实输出为硬件能力参考，重新设计并实现了
benchmark 的 SEND/RECV queue、completion、TX reclaim、RX credit、registered RX
数据路径和并行 CRC pipeline。

相同 2 GiB、64 KiB chunk、window 128、memory 场景的真实 UB provider 结果为：

```text
167.22 MiB/s -> 2246.84 MiB/s -> 2262.22 MiB/s -> 6938.63 MiB/s
```

最终达到 **6938.63 MiB/s（58.21 Gbit/s）**，相对今天开始阶段的可比基线累计
提升约 **41.49 倍**。最后一次结果同时满足：

- 2 GiB 长度完全一致；
- CRC32 完全一致；
- `cqe_error = 0`；
- SEND/RECV、credit 和 outstanding 全部闭合；
- `rx_bounce_copy = 0`；
- 8 个并行 CRC worker 生效。

相对同机 `urma_perftest send_bw` 的 **47558.59 MiB/s**，当前 verified demo 达到
约 **14.59%**，仍相差约 **6.85 倍**。二者 workload 并不相同：perftest 重复
使用固定 buffer，不解析协议、不计算 CRC、不验证数据，也不执行应用级 RX credit；
demo 的 normal profile 包含完整协议和端到端完整性验证。

## 2. 基线和参考实现

### 2.1 `urma_perftest send_bw`

真实设备同机 RC 参考结果：

```text
device:         udmac0d1e2
transport:      URMA_TM_RC
message size:   65536 bytes
JFS depth:      128
JFR depth:      512
CQ moderation:  100
throughput:     47558.59 MiB/s
message rate:   0.760937 Mpps
```

源码确认的关键 provider 使用模式：

- JFS 保持最多 128 个 outstanding SEND；
- JFR 预投递 512 个 RECEIVE；
- 每 100 个 SEND 请求一次 send completion，以 completion frontier 退休前序 WR；
- RX 每个消息仍产生 completion，并持续补充 JFR；
- hot loop 使用非阻塞 poll，不在数据路径 sleep；
- 固定注册 buffer 和可复用 WR/SGE；
- UB provider 使用 shared JFR；
- RTP 使用 provider 推荐的 priority 0。

## 3. 今天完成的优化

### 3.1 SEND queue 和 completion frontier

旧路径对每个 SEND 请求 completion，并逐条回收 TX。新路径采用 selective
completion：

```text
SEND 1..99:  unsignaled
SEND 100:    signaled
CQE #100:    retire SEND 1..100 in order
tail SEND:   forced signaled
```

未越过成功 completion frontier 的 TX slot 绝不复用；shutdown 前强制发送 tail
completion 并 drain。最新结果为：

```text
send_post     = 32770
send_cqe      = 330
send_retired  = 32770
```

每条 SEND 生命周期仍被追踪，但 send CQE 数量下降约 99%。

### 3.2 provider hot-path WR 生命周期

C shim 使用预分配 WR arena/free list，移除每个 SEND/RECV 的 hot-path
`calloc/free`。WR 只有在 send completion frontier 或 receive CQE 证明 provider
不再引用后才归还 arena。同时按 provider capability 选择 RTP priority。

### 3.3 远端 RX credit 协议

原实现只有本地 receive accounting，发送端不知道远端何时真正 repost，容易形成
RQ starvation/RNR/retry。当前语义为：

```text
receive CQE
-> slot 由接收方处理
-> slot 真正 release/repost
-> 累计 credit return
-> TCP control channel 返回 credit
-> sender 才增加发送额度
```

credit 只在 repost 成功后返回，不在 CQE 到达时提前返回。该改动使 2 GiB 吞吐从
**167.22 MiB/s** 提升到 **2246.84 MiB/s**，约 **13.44 倍**，是今天最大的
单阶段架构收益。

### 3.4 registered RX lease 和去 bounce-copy

Child 数据路径改为：

```text
RECV CQE
-> slot: PostedRecv -> RecvCompleted -> Leased
-> worker 直接读取 registered memory
-> CRC / optional positional file write
-> worker 返回 lease
-> transport thread release/repost
-> 返回 remote credit
```

安全约束：

- worker 只获得只读 memory view，不持有 provider/Segment handle；
- lease 存活期间 slot 为 `Leased`，不能 repost；
- BufferPool 在 active lease 未清零时拒绝正常注销 Segment；
- shutdown 先停止任务、join worker、回收 lease，再关闭 connection/runtime；
- file sink 使用 positional write，避免共享文件 cursor。

单 CRC worker/registered RX 阶段为 **2262.22 MiB/s**，相对 credit 修复后的
2246.84 MiB/s 只提升约 **0.68%**。它的主要价值是建立安全的零 bounce-copy
生命周期，为并行 CRC 和直接落盘提供基础。

### 3.5 更深 RX backing，和 provider credit 解耦

verified profile 的 Child RX backing 扩为 16 个 application window：

```text
window chunks:              128
window bytes:               8 MiB
registered window count:    16
RX slots:                   2048
registered RX bytes:        128 MiB
provider/JFR credit target: 512
```

注册 backing 深度不再等于 JFR credit。worker 可以持有多个 window，transport
仍可在其他 slot 上接收；JFR 深度保持 provider 已验证的 512。repost 数量同时受
逻辑 credit 和物理 free slot 限制，修复了扩展 backing 后的 `no free RX slot`。

### 3.6 并行 CRC 和 CRC combine

每个 registered RX window 独立计算 CRC32，worker 可以乱序完成，但结果按 wire
order 执行 CRC combine：

```text
window 0 CRC --\
window 1 CRC ---+-> reorder -> CRC32 combine -> final CRC
window N CRC --/
```

worker 数按进程 CPU affinity 自动选择，预留一个 transport/poll CPU；实现上限现已
从 8 提升到 32，并可用 `--crc-workers` 显式设置。该次真实运行仍为
`parallel_crc_workers = 8`。normal verified 模式仍把 CRC 和完整性验证
计入 elapsed，并未通过跳过校验提高数字。

该阶段使吞吐从 **2262.22 MiB/s** 提升到 **6938.63 MiB/s**，约 **3.07 倍**。

### 3.7 RX scatter lease

真实 provider 实验推翻了“receive sequence 连续就意味着 RX virtual address 连续”
的假设。当前 window 改为 scatter lease：

- 一个逻辑 window 可持有多个不连续 registered span；
- span 顺序严格等于 receive/wire 顺序；
- CRC 按 span 顺序更新；
- file sink 按逻辑 offset 分片 `pwrite`；
- 相邻 span 自动合并，连续场景仍是大块 CRC/写入；
- 所有 span 对应 slot 在 worker 完成前都不可复用。

同时保留 worker result 和 lease 的有序 retirement，避免乱序回收破坏 BufferPool
的局部性。这一设计不再把 provider slot 排布当作正确性前提。

### 3.8 transport-only profile

新增：

```text
--urma-profile transport-only
```

该模式为完整 payload 加 End 分配 registered RX backing；传输期间暂停 CRC worker，
收到 End 后先结束 transport timing，再执行完整 CRC 和可选文件写入。它仍要求最终
length/CRC 通过，只把 verification 时间从 transport sample 分离。

新增指标：

```text
transport_only
post_transport_verification_ns
parallel_crc_workers
```

2 GiB transport-only 需要约 2 GiB 以上注册内存和足够的 memlock。后续真实 provider
结果为 **7042.09 MiB/s（59.07 Gbit/s）**，传输后 CRC 验证耗时 115.24 ms，最终
length/CRC32 均通过。它相对 normal 的 6938.63 MiB/s 只提升约 **1.49%**，证明
8-way CRC 在该速率下已基本被传输隐藏，并不是 7 GiB/s 上限的主因。

## 5. 正确性和生命周期

优化没有用提前复用 buffer 换取吞吐。当前不变量：

```text
TX:
Free -> Allocated -> SendPosted
-> successful completion frontier covers WR
-> SendCompleted -> Free

RX:
Free -> Allocated -> PostedRecv
-> successful CQE -> RecvCompleted
-> logical scatter window -> Leased
-> CRC/pwrite finished -> transport recycle
-> Free -> repost
-> only then return remote credit
```

成功结果必须满足：

```text
integrity.ok == true
send_post == send_retired
recv_post == recv_cqe
current_outstanding_send == 0
current_outstanding_recv == 0
remote_credit_pending == 0
cqe_error == 0
```

本地代码验证覆盖 ordered CRC combine、乱序 worker 的有序 lease retirement、
scatter span CRC、direct positional file write、transport-only 延迟 verification、
release build、format 和 diff check。真实 provider 依据是上述 2 GiB integrity PASS。

## 6. 跨节点验证结论

node1（`90.91.177.158`）与 node2（`90.91.177.157`）跨节点运行时，benchmark
在 child 第一个 SEND 上报告：

```text
status=2, opcode=0, user_ctx=0x0001010100000000
```

解码为：

```text
status 2 = URMA_CR_LOC_LEN_ERR
opcode 0 = URMA_CR_OPC_SEND
user_ctx = connection 1 / generation 1 / SEND / TX slot 0
```

官方 `urma_perftest send_bw` 在相同两节点、64-byte 消息下也报告：

```text
Failed CR status 2, tot_scnt: 128, tot_ccnt: 0
```

因此已确认：TCP OOB 可达，但跨节点 UB/URMA 数据面未通过；失败发生在 CRC、scatter
lease 和 bulk Data 之前。问题范围属于 EID、TP、UB 路由、交换网络或 Uvs/UBCore
控制面环境。之前 47558.59 MiB/s 是 node1 对自身 EID 的同机结果，不是跨节点能力
证明。在官方 64-byte RC perftest 跨节点成功前，不应修改 demo 掩盖该环境问题。

## 7. 当前瓶颈

1. **Parent TX prepare/copy**：normal/transport-only 的 Parent 约 290 ms CPU / 291 ms
   wall；fixed-TX 后降为 38.7 ms CPU，并把吞吐提升到 15224.02 MiB/s。这是当前最
   明确的单项瓶颈，主要不是 URMA SEND 本身。
2. **Child CRC/内存带宽**：fixed-TX 运行的 Child 为 1067.09 ms CPU / 134.52 ms
   wall，平均约 7.93 CPU，8 个 worker 已饱和并开始限制 lease 回收/credit。需要用
   deferred verification 或更多 worker 分离它。
3. **RX CQ batch**：32770 个 receive CQE 对应约 32761 次有效 poll，平均接近逐
   CQE 处理，与 perftest 的紧凑 C hot loop 仍有差距。
4. **应用 credit 往返**：253 次 credit update/wait 保证生命周期安全，但可能形成
   burst/stall，需要在不提前复用 slot 的前提下继续调优。

## 9. 2026-08-20：组合 profile 与可配置 CRC worker

新增实验 profile：

```text
--urma-profile fixed-tx-transport-only
```

它组合两种已经独立验证过的诊断路径：Parent 重复使用完成注册且内容不可变的 TX
payload，Child 为完整 payload 保留 registered RX backing，并在 transport timing
结束后再做 CRC combine。最终仍执行 length/CRC32 校验，RX lease 在校验完成前也不会

## 10. 2026-08-20：fixed-TX常量空间初始化

fixed-TX CLI不再调用`MemorySource::generate(transfer_bytes)`。它现在只保存逻辑传输
长度，并仅创建实际发送的一个immutable registered chunk。因此Parent初始化的源数据
空间由O(transfer bytes)降为O(chunk size)，2/8/64 GiB测试不再分别分配和扫描对应大小
的完整`Vec`。

fixed payload的expected CRC也从逐chunk重复扫描改为CRC combine二进制倍增：先计算
一个chunk的CRC，再以O(log chunk count)次combine得到完整逻辑payload的CRC。单元测试
已验证0、1及多次重复时与原线性算法完全一致。

该改动不改变steady-state SEND hot path、payload内容、WR数量、completion、RX校验和
计时边界，预期不会降低传输性能；它只消除计时前的无效分配、生成和CRC扫描。当前已
通过format、feature-off check、14项URMA fast-path单元测试及feature-on release build，
真实provider启动时间与吞吐仍待复测。

## 12. 2026-08-20：真实文件直接填充 registered TX

在 fixed-TX 已达到 64 GiB、389.23 Gbit/s 的硬件能力基线后，优化重点转回真实
payload。file scenario 的 Parent 路径由：

```text
pread -> 普通 Vec -> memcpy -> registered TX slot -> SEND
```

改为：

```text
分配 registered TX slot -> pread 直接填充 slot -> SEND
```

这与当前 Dragonfly `RangeReader` 使用共享文件和 positional `read_at`、复用 owned
buffer 的模式一致；但 demo 仍采用 SEND/RECV registered staging，并没有宣称实现
Dragonfly 的完整 RDMA transport。

WR 生命周期保持为：

```text
Free -> Allocated -> 临时可写 fill closure -> Posted
     -> signaled completion frontier retirement -> Free
```

只有 `Allocated` 且尚未被 WR 引用的非 alias TX slot 能取得临时可写 slice。slice
不能逃逸 closure；fill 失败立即释放 slot；post 失败回滚 `Posted`；post 成功后仍由
原 completion frontier 统一回收，因此 buffer 不会提前复用。raw pointer 继续限制在
FFI/shim 内部，shim ABI 升为 7。

新增 Parent 统计：

```text
direct_file_tx
file_pread_calls
file_pread_bytes
file_pread_ns
```

其中 `file_pread_ns` 只统计实际 positional read，不包含 SEND post 和 CQ polling。memory、
fixed-TX 及 Child registered RX/CRC/pwrite 路径不变。本地 URMA benchmark 28 项单元测试和
ABI 基线通过；真实 provider 上的文件吞吐、页缓存/磁盘影响与 shutdown 尚待验证。

## 13. 2026-08-20：4 MiB registered TX 批量读取

真实 provider 的 8 GiB 文件与 2 GiB tmpfs 复测分别只有 2347.90 MiB/s 和
2189.44 MiB/s。两者 `file_pread_ns / elapsed` 均约 98%，Parent system CPU 也接近
单核 100%，证明瓶颈不是物理磁盘，而是每个 64 KiB SEND 前串行执行一次 positional
read。设备 `max_msg_size=65536`，不能通过增大单 WR payload 绕过。

file TX 因此改为按发送 window 分批：window=64、chunk=64 KiB 时，一次分配物理连续
的 64 个 registered TX slots，对完整 4 MiB span 只执行一次 `pread`，随后仍提交 64
个各 64 KiB 的合法 SEND WR。每个批次最后一个 WR 强制 completion，使 batch 在任何
CQ moderation/window 组合下都能形成明确的 retirement frontier；下一批填充前先确保
上一批全部 completion-retire。

生命周期为：

```text
64 slots Free -> 整批 Allocated -> 一次 bounded mutable fill
-> 逐 slot SendPosted -> batch-tail completion frontier
-> 逐 slot SendCompleted/Free -> 下一批
```

fill 失败释放整批；部分 post 失败只释放尚未提交的 slots，已经提交的 WR 仍由 connection
shutdown drain，绝不提前复用。尾批只允许最后一个 slot 短于 64 KiB，确保一次 packed
pread 后每个 SEND offset 仍落在对应 slot 边界。

新增统计 `file_tx_batch_count` 和 `file_tx_batch_max_bytes`。2 GiB/window64 的预期值为
512 和 4194304，理想情况下 `file_pread_calls` 也从 32768 降至约 512。当前本地
feature-on URMA benchmark 29 项单元测试通过；真实 provider 性能待复测。

## 14. 2026-08-21：对齐 Dragonfly 候选 RDMA 路径的 mmap + 双 TX ring

4 MiB 批量 `pread` 将 syscall 数降低 64 倍，但真实 provider 上 8 GiB file scenario
仍只有约 2344 MiB/s；`file_pread_ns` 约占 elapsed 的 95%，说明瓶颈已经从小 syscall
变成单线程 page-cache 到 registered memory 的内核 copy。作为对照，dynamic memory
约 7057 MiB/s，而 fixed-TX transport baseline 已达到约 389--406 Gbit/s。此阶段目标
因此不是让真实文件复制等同 perftest，而是逼近 Dragonfly 实际 finished-piece 上传路径。

当前本地 Dragonfly2 候选 RDMA 分支（不是上游 main 的既定实现）有两个可直接借鉴的
模式：finished piece 可建立只读 mmap；发送端使用两个 registered windows，在 NIC
消费 window A 时填充 window B。它仍然执行 mmap/page-cache 到 registered send ring
的 copy，并不是把任意文件页直接注册为 MR，也不是 one-sided 直接落盘。

demo 的 normal memory/file source 现统一为 window producer：

```text
finished file -> MAP_PRIVATE read-only mmap
                 -> copy 4 MiB into registered TX window A -> 64 SEND WR
                 -> copy 4 MiB into registered TX window B while A outstanding
                 -> wait A batch-tail completion frontier
                 -> post B; refill A; repeat
```

若 mmap 建立失败，file scenario 自动回退到现有批量 `pread`，协议和完整性语义不变。
映射在 START/steady-state 计时前建立，并使用 best-effort `MADV_SEQUENTIAL` 与
`MADV_WILLNEED`；实际 page fault 和每个 window 的 registered-memory copy 仍可能落入
payload 时间。benchmark 要求 source 在传输期间是不可截断、不可变的 finished file，
否则普通 mmap 本身存在 SIGBUS 风险。

TX 生命周期增加了显式 `PreparedTxBatch` ownership：

```text
Free -> Allocated/Prepared（CPU 可写，provider 尚无引用）
     -> SendPosted（CPU 不可写）
     -> batch-tail signaled CQE 覆盖的 retirement frontier
     -> Free
```

prepared batch 必须被 post 或显式 discard。等待 credit、drain 或 post 前失败会释放尚未
提交的 slots；部分 post 失败只释放未提交的尾部，已提交 WR 留给 connection shutdown
drain。双 ring 不要求新增 provider API，也不改变 64 KiB `max_msg_size`、shared JFR、
RX credit、CRC combine 或 Child registered-window lease 语义。

新增 Parent 统计：

```text
file_mmap_tx
tx_fill_bytes
tx_fill_ns
tx_fill_overlap_batches
tx_ring_windows
```

window=64、tx_slot_count=128 且传输超过一个 batch 时，预期
`tx_ring_windows=2`、`tx_fill_overlap_batches>0`、mmap 成功时
`file_mmap_tx=1` 且 `file_pread_calls/file_pread_ns=0`。本地 mmap 内容测试、17 项 URMA
benchmark fast-path 单元测试通过；feature-off check 和 feature-on release build 通过。
完整 lib test 分别执行到 81/84 与 98/101，其余 3 项均因当前 sandbox 禁止 TCP bind
（`EPERM`）失败，与本次路径无关。真实 provider 性能仍待复测，不能仅凭设计宣称收益。
