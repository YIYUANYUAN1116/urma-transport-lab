# URMA file-to-file 后续优化与 Dragonfly 适配路线（2026-08-21）

## 1. 结论

当前同节点实验已经证明 URMA fixed-TX 数据面达到 `389～406 Gbit/s`，与
`urma_perftest send_bw` 的约 `398.95 Gbit/s` 对齐。mmap file-to-file 当前约
`43～44 Gbit/s`，主要限制已经转移到 Parent 文件页到 registered TX 的 copy、Child
CRC32/pwrite 以及 storage credit 反压。

后续目标不应是让单个 8 GiB 文件达到 perftest，而应把已验证的数据面收敛成可嵌入
Dragonfly 的 Piece 传输引擎，并优化多 Piece 聚合吞吐、CPU 成本和注册内存预算。

证据口径：

- fixed-TX/file-to-file 数字：同节点真实 provider 实验确认；
- linked WR、`bad_wr`、UDMA doorbell：当前 UMDK 源码确认；
- Dragonfly engine/Piece/Storage 映射：当前本地 Dragonfly2 候选源码确认或架构推断；
- 跨节点性能和多 Piece 聚合收益：尚待环境验证。

## 2. 当前层次和瓶颈

| 路径 | 已测性能 | 当前主要限制 |
|---|---:|---|
| fixed-TX transport | `389～406 Gbit/s` | 已接近 provider/hardware 能力 |
| dynamic memory TX | 约 `60 Gbit/s` | Parent 单核填充 registered TX |
| mmap file-to-file | 约 `43～44 Gbit/s` | mmap copy、CRC32、pwrite、storage credit |
| TCP file-to-file | 约 `13～16 Gbit/s` | TCP 内核路径和文件 I/O |

单文件 dynamic/file 路径不能直接套用 perftest 目标。perftest 复用已经注册的固定 payload，
而文件传输必须生产 payload、保持数据完整性并等待持久化路径释放 RX ownership。

## 3. 优化优先级

| 优化项 | 单流收益预期 | Dragonfly 适配价值 | 优先级 |
|---|---:|---:|---:|
| JFS/JFR linked WR batch post | 中，CPU 收益明确 | 很高 | P0 |
| 整窗口 registered buffer/lease | 中 | 很高 | P0 |
| 进程级共享 CQ progress engine | 单流有限，多流高 | 必需 | P1 |
| 全局注册内存池与 byte budget | 单流有限 | 必需 | P1 |
| 多 Piece 并发 | 高 | 必需 | P1 |
| NUMA/CPU affinity | 可能明显 | 高 | P1 |
| SEND_IMM + shared JFR 路由 | 性能收益小 | 中高 | P2/验证项 |
| URMA READ/WRITE | 不确定 | 当前低 | 暂缓 |

## 4. Linked WR batch post

### 4.1 源码依据

UMDK 的 `urma_jfs_wr_t` 和 `urma_jfr_wr_t` 都有 `next` 指针。`urma_perftest` 提供
`--jfs_post_list/-l` 和 `--jfr_post_list/-r`，预构造链表后一次调用 post API。

当前 UDMA SEND provider 遍历整个 WR list，构造多个 WQE 后统一执行 barrier 和 SQ
doorbell update；失败时 `bad_wr` 指向第一个未成功提交的 WR。JFR provider同样逐项处理并
返回 `bad_wr`。

### 4.2 Lab 实现状态

本轮已经实现：

- shim ABI 从 7 升到 8；
- 新增 pointer-free `urma_lab_wr_desc_t`；
- 新增 `urma_lab_post_send_batch` 和 `urma_lab_post_recv_batch`；
- C shim 在自己的 WR arena 中建立稳定 `next` 链；
- SEND payload window 由逐 WR post 改为整批 post；
- RX initial/replenish credit 由逐 WR post 改为整批 post；
- 保留 completion moderation，批次尾 WR 强制 signaled；
- `bad_wr` 之前的已提交前缀继续由 CQE/shutdown drain 管理；
- 未提交后缀回滚为 Allocated 后释放，绝不把可能 provider-owned 的 buffer 提前复用；
- provider 异常返回错误但没有 `bad_wr` 时，保守地把整个链视为可能已提交，不提前释放；
- 新增 `send_post_calls`、`recv_post_calls`、`send_post_list_max`、
  `recv_post_list_max` 统计。

当前验证状态：feature-off 全量测试通过；feature-on C shim/bindgen/Rust 全目标编译通过，
shim ABI 与 Done 控制帧测试通过；linked WR 的真实 UDMA provider 行为和性能尚未在本轮环境
运行，不能标记为真机验证完成。

预期 8 GiB、64 KiB chunk、window=64 时：

```text
send_post（逻辑 WR）       ~= 131074
send_post_calls（API调用） ~= 2048 + 控制消息
send_post_list_max         = 64
```

RX 初始 credit 可能形成比 payload window 更长的 list，因此应以实际
`recv_post_list_max` 为准。

### 4.3 生命周期

```text
Prepared batch
-> 所有 slot 标记 SendPosted/PostedRecv
-> C shim acquire WR owners并建立next链
-> 一次provider post
-> 成功前缀track到CompletionPoller
-> 未提交后缀rollback/release
-> signaled CQE建立SEND retirement frontier
-> frontier之前的WR owner和TX slots一起释放
```

部分提交错误会结束当前连接；已提交前缀不能继续作为正常业务流使用，但其 buffer 仍保持
provider-owned，直到 completion/flush 或最终安全隔离，不会为恢复吞吐而提前复用。

## 5. 面向 Dragonfly 的 registered window

生产适配器应逐步从任意 slot 集合收敛到整窗口资源：

```text
RegisteredWindow
  registration / base / length
  chunk descriptors
  transfer ID / piece offset / generation
  receive progress
  storage lease
  lifecycle state
```

推荐状态：

```text
Free -> Posted -> Receiving -> Complete -> StorageOwned -> Reposting -> Free
```

CRC 和 positional write 可以并行读取同一个只读 lease；两者都结束前不能 repost。建议先
增加 `rx_window_span_count` 和 `pwrite_calls_per_window`，确认当前 scatter 程度。如果窗口通常
已经是一个连续 span，重构价值主要体现在生命周期、池化和集成兼容性，而不是单流吞吐。

## 6. 进程级 UrmaEngine

Dragonfly 适配不应为每个 Piece 重建硬件资源。推荐结构：

```text
UrmaEngine（进程级）
├── Device / Context
├── shared JFC / shared JFR
├── dedicated CQ progress thread
├── RegisteredWindowPool
├── RegistrationBudget
├── Jetty/session registry
└── Pending WR slab（含generation）

PieceTransfer（请求级）
├── Piece metadata
├── 1～2个TX/RX window lease
├── sequence / offset
├── pending completions
└── cancellation/shutdown state
```

这与本地 Dragonfly2 候选 RDMA 实现的 shared Fabric、CQ progress、registered buffer
pool 和 per-Piece operation ownership 方向一致。

## 7. 多 Piece 性能模型

下一阶段建议用更接近 Dragonfly 的 workload：

```text
piece size: 64 MiB
chunk:      64 KiB（provider上限）
window:     32 / 64 WR
RX ring:    每Piece 1～2个window，受全局JFR/内存预算约束
concurrency: 1 / 2 / 4 / 8 / 16
```

Piece 内保持有界和有序，并行度主要来自多个 Piece，而不是给一个 8 GiB 文件持续增加 CRC
worker。必须同步限制：总注册内存、RX WR、outstanding SEND 和 storage blocking tasks。

## 8. Storage、shared JFR 与 NUMA

- Demo 当前 window 处理仍会创建临时 write thread；真正接入 Dragonfly 时应复用 Tokio
  blocking pool，并设置有界 admission，不复制一套无限 worker 模型。
- UB/UDMA 使用 shared JFR。多 Jetty/Piece 时可以研究 `SEND_IMM` 携带 compact transfer
  slot、generation 和 window sequence，由共享 progress engine 路由 CQE；API 已源码确认，
  provider行为仍需真机验证。
- 400 Gbit/s 级别需要验证 NIC、CQ progress CPU、registered memory first-touch、CRC worker
  和 storage worker 的 NUMA locality。

## 9. 暂不推进

- 不改成 one-sided READ/WRITE；当前 SEND/RECV 更接近 Dragonfly 候选实现，且 ownership、
  notification、cancel 和 shutdown 更清晰。
- 不突破 provider 的 64 KiB 单 WR payload 上限；4 MiB 是应用窗口，不是单条消息。
- 不使用整文件 registered RX 作为生产结构。
- 不以增加单文件 CRC worker 代替 Piece 并发。
- 不弱化 completion、buffer ownership、integrity 或 shutdown 安全换取 benchmark 数字。

## 10. 验证顺序

1. feature-off fmt/check/test；
2. feature-on compile/test；
3. 真机 fixed-TX 对比 linked post 前后的吞吐、CPU 和 post-call 统计；
4. 真机 mmap file-to-file 复测；
5. 分别测试 window `32/64/96/128`，确认 list size 最佳点；
6. 完成跨节点 perftest 和 demo 环境修复；
7. 再实现 Piece 并发与进程级 UrmaEngine 原型。

## 11. 第一轮真机结果与修正

第一轮 8 GiB、window=64 实验确认 mmap file SEND batch 已生效：

```text
send_post=131074
send_post_calls=2050
send_post_list_max=64
throughput=42.66 Gbit/s
integrity.ok=true
```

相对改动前约 `44.16 Gbit/s` 没有单流吞吐收益，约低 `3.4%`，说明该优化当前主要价值是
减少 provider API/doorbell/锁开销，为多 Piece 并发释放 Parent CPU，而非提高受 copy/storage
限制的单文件上限。需要至少三次重复实验后才能判定小幅差异是否稳定。

同轮 fixed-TX 输出显示 `send_post_calls=send_post=131074`、`send_post_list_max=1`，证明
fixed profile 仍经过旧的逐条 aliased-TX 入口，不能用该次 `321.10 Gbit/s` 评价 linked SEND。
现已增加 aliased registered payload 的批量 slot/WR 构造，并让 fixed profile 按 application
window 调用同一个 linked post 入口；该修正已编译和测试，等待第二轮真机验证。

RX 已确认支持 linked post，初始 `recv_post_list_max=512`；payload 期间
`recv_post_calls=17865～35725`，说明 sink 返回 slot 的时间较碎，后续若要继续降低 RX
doorbell，需要按 registered window 聚合 repost，而不是简单扩大一次调用允许的最大 list。

第二轮 fixed-TX 的 64-WR linked list 达到 `328.63 Gbit/s`，虽然 post calls 已正确降至
2050，但 `remote_credit_wait_ns=54.80 ms`，约占 209.11 ms 样本的 26%。问题不是 WR
lifetime，而是把 application window、credit wait batch 和 provider post-list 都绑定为 64，
形成“等满 64 credit 才发”的批次屏障。

现已新增 `--urma-post-list N`，默认 16，并将三个量解耦：

```text
application window     = --window
SEND completion周期    = min(window, 100)，window尾确保frontier
provider linked list   = --urma-post-list
```

fixed-TX 会按 post-list 粒度等待 credit 和提交，但在 application window 未满时持续追加，不会
每个 post-list 都 drain，也不会为每个 list 强制 CQE。file TX 仍以 4 MiB producer window
填充 registered memory，再将其中 64 个 WR 拆成指定长度的若干 provider post。结果新增
`configured_send_post_list`，便于确认实验参数。

### File sink 尾部排空与持久 worker

8 GiB mmap file-to-file 单次实验中，post-list 1 的 Child 用时 2.3389 s，但 Parent 已在
1.5329 s 完成发送，Child 在 End 后仍有约 806 ms 的 sink 尾部排空；post-list 32 的对应
差值只有约 13.7 ms。两者 `tx_fill_ns` 分别为 1.2394 s 和 1.2420 s，说明 42.8 Gbit/s
样本的主要变化来自 RX sink 调度，而不是文件 producer 或 linked SEND 本身。

这里的 `tx_fill_ns` 是 mmap 文件页到 registered TX ring 的 measured copy 时间，包含潜在
page fault/cache access，不是纯磁盘 read；mmap 样本的 `file_pread_calls=0`。

源码复核确认 RX lease 会将物理相邻 slot 合并为一个 span，但旧 file worker 为每个 4 MiB
window 再创建一个 scoped OS thread，使 8 GiB 传输产生 2048 次临时线程创建。现已改为：

```text
persistent sink worker
  -> CRC registered RX spans
  -> one pwritev call for all spans when the kernel accepts the full vector
  -> emit one combined outcome
  -> wire-order CRC combine and lease reclaim
```

partial `pwritev` 会按实际写入字节推进 iovec 和文件 offset；lease 只有在 CRC 与完整写入均
结束后才进入按序回收路径。控制协议升级到 v4，并将下列指标同时带回 Parent 结果：

```text
sink_transport_receive_ns
sink_drain_ns
sink_outstanding_at_end / sink_pending_at_end
sink_max_outstanding / sink_max_pending
sink_jobs
sink_queue_wait_ns / sink_queue_wait_max_ns
sink_processing_ns / sink_processing_max_ns
sink_pwrite_calls / sink_pwrite_bytes
sink_pwrite_ns / sink_pwrite_max_ns
sink_crc_ns / sink_crc_max_ns
sink_span_total / sink_span_max
sink_transient_thread_spawns
```

其中累计 worker 时间允许大于 wall time。当前实现已通过编译和本地 fragmented-span
`pwritev`/完整性测试，真实 UDMA provider 与目标文件系统上的性能仍待验证。
